## Who fills what

A planner can start with a brief, one structured field, or both. Saving a blocked review is supported. The exact merchandising intake for future seller campaigns still needs Big’s next specification. The current screen exposes only fields accepted by this version.

| Input | Planner’s part | Backend’s part |
|---|---|---|
| Product and pack | Describe the product or selling pack. Explicitly select a returned exact choice or confirm a quoted suggestion. | Supply the catalog options, choice/product/pack IDs, supported offers, timezone and category. Product and pack hints are optional for the runnable choice. The current catalog contains a single **synthetic 12-roll toilet-tissue listing on Shopee**. |
| Channel | May enter a platform name, including an unsupported one. | Normalize the name, retain unsupported intent with a blocker, and derive Shopee if the selected demo listing has no entered channel or pending channel suggestion. |
| Audience and objective | State the audience and objective. | Resolve segment IDs and measurement support. The current synthetic evaluator requires all eligible buyers and incremental profit. |
| Budget and dates | Give a total subsidy cap in THB and a first active and first inactive date. A supplied zero is valid input. | Resolve relative interview dates in the market timezone, ask for confirmation, and add the post-campaign measurement window. The general readiness window is up to 56 days. This evaluator accepts 1–42 active days plus 14 follow-up days. |
| Offer | Describe one offer. Structured intent can include kind, value, unit, minimum spend, redemptions per shopper, and eligibility. Some requested mechanics save as blocked. | Resolve exact terms, funder, stacking and eligible orders. For broad all-buyer intent, missing eligibility can be derived as `all`. Current execution supports 0.01–30% off or a 0.02–30 THB whole-satang voucher without threshold or per-user cap. |
| Costs, policy and evidence | Review the supplied evidence and approve the exact revision. | Supply costs, their basis and source, immutable data versions, aggregate segment statistics, seeds, assumptions, baseline, conservative alternative and decision gates. A confirmed cost with source `default` is a synthetic policy assumption. |

The frontend submits neither seller fee schedules nor hand-entered unit economics on v1. Synthetic assumptions currently include a THB 100 regular price, THB 60 COGS per pack, and no fees or paid media. Commercial seller coverage still depends on applicable verified evidence. [Catalog and policy](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/api/v1_catalog.py)

## Request flow

All paths are relative to `/api/v1`. The JSON API serves a single trusted local planner. The browser sends no API keys and uses the server’s configured planner identity. A separately hosted frontend can set `VITE_API_BASE_URL` to the backend origin and add the frontend origin to backend `CORS_ORIGINS`. Vite proxies same-origin requests to port 8000. [Client](../src/v1/client.ts) · [Generated wire declarations](../src/v1/schema.d.ts)

| Operation | Request | Response and interaction |
|---|---|---|
| POST /campaign-reviews | Nonempty brief up to 1000 characters, sparse planner fields, or both | 201 saves the first revision. Present the highest-priority question, other open questions, current facts, origins and quoted candidates. |
| GET /campaign-reviews/{review_id} | Current interaction ID | Restore the latest saved review when the tab reloads. The browser preserves its local transcript and current run link in tab session storage. The API returns current facts, candidates and questions. |
| POST /campaign-reviews/{review_id}/revisions | `base_revision` with either a natural-language `answer` up to 1000 characters, or structured `edits` and/or `confirm` candidate IDs | An answer creates its own revision. Present quotes from the brief or answer and explicitly confirm candidate IDs from the **current** revision. Local deterministic extraction remains available without an LLM key. Edited fields replace their complete value, including an edited offer. Null clears a field. Omitted fields carry forward. A stale 409 returns the latest review for a manual rebase. |
| POST /campaign-reviews/{review_id}/approvals | `revision` and explicit `confirmed: true` | Returns the receipt for that exact ready revision. A new revision requires renewed approval. |
| POST /runs | `approval_id`, client `submission_id`, and optional `retry_of_run_id` | First submission returns 202. Reuse its ID after a lost response. An identical repeat returns the existing run. A retryable terminal failure takes a fresh ID with its parent run. |
| GET /runs/{run_id} | The accepted run’s status URL | Follow server poll intervals while pending. The current local synthetic screen normally finishes during submission. A terminal error carries the failure and retryability. |
| GET /runs/{run_id}/report | The completed run’s report URL | Display the evaluation, percentiles, scalar probabilities, unavailable reasons and per-plan inputs/results when returned. Validate the run, review, approval and revision identity. |
| GET /runs/{run_id}/input | Accepted run ID | Returns the exact approved review used by the evaluator, including facts, origins, assumptions and costs. Join `run_id` and `approval_id` plus the nested review’s ID and revision. |
| GET /runs/{run_id}/evaluation | Completed run ID | Returns the recorded decision, original-plan checks, comparisons and measurement window. Join run, review, approval and revision. Render each returned condition and threshold, including availability checks without numeric limits. A legacy report may return `checks_unavailable_reason`. |
| GET /runs/{run_id}/historical-comparison | Completed run ID | Join run, approval and revision. Show the pinned case, limitations, observed lift range and prediction only to the extent supported by its status. Missing evidence is an HTTP 200 outcome. |

## Results and Arena scope

The connected Arena shows real per-plan aggregate results for the selected run. The overhead and isometric maps illustrate its setting. The workflow traces the reviewed intent, approved revision, selected offer and budget, paired simulations, original-plan policy and recorded decision. Its stage details use the report and the matching review already in the browser. Changing a plan updates the comparison and result stages. The original decision stays tied to the submitted plan. Historical evidence and recorded checks load when requested in Verdict. Only scenarios included in the selected plan’s report are offered. The synthetic evaluator compares the submitted offer, a conservative half-discount alternative, and the paired no-campaign baseline in **S1**. The verdict applies to the submitted plan. It exposes frozen inputs and the reasons for alternative changes. The app uses the backend’s decision and never infers a recommendation from a chart. Missing ROAS, buyer coverage or other metrics retain their reason codes. [Evaluator](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/engine/synthetic.py)

V1 returns aggregate comparisons. Shopper IDs, per-shopper traces and per-day map frames have no v1 endpoint. The selectable shoppers and rival scenarios in **Demo arena** use a labeled, independent fixture. The app keeps that walkthrough separate from submitted v1 results. An engine-backed Arena will need an agreed observation stream or read model covering timeline grain, stable simulated IDs, per-plan and per-scenario identity, preference state and companion traces.

## Historical evidence and decision checks

A historical reference comes from the Complete Journey dataset. It records the fit cutoff, inclusive retail-week windows, category and offer match criteria, and observed **control-adjusted category sales lift in percentage points**. The historical range and simulated incremental profit in THB measure different outcomes. An older run can return `unavailable / snapshot_missing`. A newly pinned reference can return `reference_only / prediction_missing`. The schema reserves `inside_range` and `outside_range` for a compatible held-out prediction. The current run handler supplies the pinned observation to the adapter without a prediction artifact. [Reference matching](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/api/historical_reference.py) · [Comparison adapter](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/api/historical_prediction.py)

The synthetic decision checks include the availability of median subsidy leakage, a median incremental profit target when supported, and the approved maximum loss probability. A leakage check marked `pass` means a leakage estimate exists. The response gives its observed fraction and leaves its threshold null. The larger campaign-comparison contract lives in a separate proposal. [Check implementation](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/api/v1_evaluation.py) · [Proposed comparison contract](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/0c3e6a2/docs/campaign-comparison-v1.proposed.openapi.yaml)

### Shopper groups and weekly counts for Big

Verified on backend `dev@7446a7d`. A shopper in the weekly engine first chooses a would-be brand group, then buys or skips purchasing at that group’s price. There are exactly three brand groups. Waiting is a purchase outcome for some nonbuyers. The engine does not track an undecided brand. [Shopper choices and purchase step](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/7446a7d/engine/shopper.py)

| Engine group | Meaning for an Arena storefront |
|---|---|
| `US` | The catalog currently assigns manufacturer 751 the display name Cellox and marks it as ours. These two labels have `default` provenance. |
| `RIVAL` | One combined rival choice. Its starting share comes from the largest non-ours manufacturer, currently 764 (Scott). Each week the deepest active match or undercut determines its discount, so its purchases cannot all be attributed to Scott. |
| `OTHER` | All remaining market share, including smaller manufacturers that may have their own rival policies. Separate sales by those manufacturers would require individual brand choices in the shopper engine. |

The live v1 report contains aggregate scenario metrics. It exposes neither a shopper-group directory nor weekly purchase counts. The separate fixture API’s `ContextPack.rivals[].rival` and report’s `competitive` data describe competitors and reactions. Neither identifies the shopper groups. Catalog display names and the historical dataset’s retail-week windows serve different purposes from weekly simulated transactions. [Catalog and provenance](https://github.com/NEVERHOT-Team/campaignTwin-backend/tree/7446a7d/data/processed) · [Fixture routes](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/7446a7d/api/routes.py) · [Published v1 schemas](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/7446a7d/docs/campaigntwin-api-v1.openapi.yaml)

**Proposed backend addition, pending agreement.** Publish a group directory with stable IDs, run-pinned group-level labels and their sources. A label such as “Rival offer” describes the combined rival group. “Scott” identifies only the current share prior. For each run, approved revision, plan, scenario and modeled week, provide a list keyed by group ID with one completed-purchase count per published group, plus total population, total nonbuyers and waiting nonbuyers. Today’s engine would supply three entries. State the count unit and the seed or aggregation method. Today `WeekStats` has `buyers_us`, `buyers_rival`, `buyers_other` and `waiting`. Its counts scale simulated shoppers to represented households. `week_row()` retains `buyers = buyers_us`, `from_rival` and `waiting` alongside sales and profit. `from_rival` is already included in our buyers and uses prior brand state, initialized from preference. Rivals’ and other brands’ purchase counts must be carried forward before the weekly row discards them. [Weekly row adapter](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/7446a7d/engine/shopper.py) · [Across-seed aggregation](https://github.com/NEVERHOT-Team/campaignTwin-backend/blob/7446a7d/engine/evaluator.py)

For a **share of all shoppers** view, divide each group’s buyers and total nonbuyers by the same modeled population for that week. For **share of buyers**, divide a group’s buyers by total buyers across all published groups on the same basis. For **waiting among nonbuyers**, divide waiting by total nonbuyers. Waiting counts nonbuyers whose learned waiting factor is below one. Within a population chart, break nonbuyers into waiting and remaining nonbuyers only once. Calculate shares from a consistent population and seed basis before separate rounding or medians. A zero denominator yields an unavailable percentage. Missing observations must stay unavailable in the connected Arena.
